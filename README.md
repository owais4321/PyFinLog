# PyFinLog

## Artifact Overview

PyFinLog is a Python toolkit for executable logical specifications
and explicit-state verification.

The artifact provides:

- Propositional expression construction and evaluation.
- Interpreted predicates and finite-domain quantification.
- Scoped witnesses and counterexamples.
- Propositional satisfiability, validity, equivalence, and entailment.
- Explicit-state invariant checking.
- Structural deadlock detection with allowed termination states.
- Shortest counterexample paths with named transitions.
- Counterexample replay.
- Automated tests and a reproducible evaluation script.

PyFinLog combines concrete logical evaluation with transition-system exploration.
It does not implement unrestricted first-order theorem proving, SMT reasoning,
or general temporal-logic model checking.

## 1. Requirements

### Required

- Python 3.10 or newer.
- A terminal.
- The complete artifact directory.

The checking engine, demonstrations, tests, and standard evaluation use only
the Python standard library. They do not require external solvers, network
access, credentials, GPUs, or external datasets.

### Optional

Installing PyFinLog as a package requires pip and setuptools. Package installation
is not necessary to evaluate the artifact from its root directory.

## 3. Quick Start for Artifact Evaluators

Open a terminal in the artifact root directory.

### Step 1: Confirm Python

```bash
python --version
```

The version must be 3.10 or newer. Use `python3` instead of `python` if that is
the appropriate executable on your system.

### Step 2: Check Imports

```bash
python -c "from logic_core import Variable, valid; p = Variable('p'); print(valid(p | ~p).status)"
```

Expected output:

```text
valid
```

### Step 3: Run Smoke Tests

```bash
python smoke_test.py
```

Expected outcome: all smoke tests pass and the final unittest verdict is `OK`.

### Step 4: Run the Complete Test Suite

```bash
python -m unittest discover -v
```

Expected outcome: all discovered tests pass and the final verdict is `OK`.

The smoke-test file is executed separately because its filename does not match
unittest's default `test*.py` discovery pattern.

### Step 5: Run the Technical Demonstrations

```bash
python examples.py
```

Expected outcome: all demonstrations complete without assertion failures.

### Step 6: Reproduce the Evaluation

```bash
python evaluation.py --runs 10 --output evaluation_results_review
```

Expected outcome:

- Unit tests pass.
- Differential correctness checks find no mismatches.
- Benchmark verdicts match the expected faulty or corrected model behavior,
  or are explicitly reported as `unknown` if an exploration budget is reached.
- Evaluation files are created in `evaluation_results_review/`.

Runtime depends on the Python implementation and host machine. Timing values
are not expected to match an included reference run exactly.

Run these commands without Python's `-O` option, because demonstration scripts
use assertions to check expected behavior.

## 5. Demonstration Guide

Individual demonstrations can be selected:

```bash
python examples.py access
python examples.py witnesses
python examples.py entailment
python examples.py protocol
```

### 5.1 Access-Control Specifications

The access-control demonstration checks:

- Authorization safety: every granted request is permitted.
- Availability: permitted requests are granted.
- Separation of duties.
- A deliberately faulty policy.
- A corrected policy.
- A deny-all policy that satisfies safety but violates availability.

Expected results:

| Check | Expected result |
| --- | --- |
| Faulty authorization policy | `violated` |
| Corrected permission relation | `holds` |
| Deny-all safety | `holds` |
| Deny-all availability | `violated` |
| Separation of duties in the supplied role model | `holds` |

The faulty policy identifies Bob's access to payroll as an unauthorized grant.

This example also illustrates why a safety implication alone does not establish
that authorized operations remain available.

### 5.2 Dependent Quantified Witnesses

The worker-allocation demonstration distinguishes:

```text
For every job, there exists a suitable worker.
```

from:

```text
There exists one worker suitable for every job.
```

Expected results:

- Per-job coverage holds.
- `job_a` has witness `worker_1`.
- `job_b` has witness `worker_2`.
- The single-worker property is violated.
- Adding unsupported `job_c` produces an outer counterexample for that job.

Witnesses remain attached to the enclosing variable assignment.

### 5.3 Requirements Consistency and Entailment

The requirements demonstration checks:

- Whether a set of requirements has a satisfying Boolean assignment.
- Whether safety follows from those requirements.
- Whether requests imply service without authorization.
- How contradictory premises create vacuous entailment.

Expected results:

- The consistent requirements are satisfiable.
- Authorization safety follows from them.
- Unconditional service has a countermodel.
- Contradictory requirements are unsatisfiable.
- Classical entailment from contradictory premises is valid.

The final result is a property of classical logic, not evidence that an
inconsistent specification is useful.

### 5.4 Authorization Protocol and Lock-Order Deadlocks

The protocol demonstration uses the core model-checking API.

Expected results:

| Model | Expected result | Evidence |
| --- | --- | --- |
| Faulty authorization protocol | `violated` | Path actions: `request`, `grant` |
| Corrected authorization protocol | `holds` | Four reachable states checked |
| Opposite lock acquisition order | `deadlock` | P0 acquires A; P1 acquires B |
| Consistent lock acquisition order | `deadlock_free` | Twelve reachable states checked |
| Corrected protocol with insufficient state budget | `unknown` | Exploration incomplete |

The deadlock model explicitly distinguishes successful termination from an
unexpected state with no enabled transitions.

### 5.5 Combined Demonstration

```bash
python main.py
```

This executes the basic logical examples, access-control checks, and named
transition-system demonstrations.

## 6. Reproducing the Evaluation

Run:

```bash
python evaluation.py --runs 10 --output evaluation_results_review
```

The script defines its own parameterized models and does not require changes
to the demonstration files.

An existing output directory is reused, and its result files are overwritten.
Use a distinct output directory to preserve different runs. Do not run multiple
evaluations concurrently against the same output directory.

### 6.1 Correctness Evaluation

| Evaluation component | Method |
| --- | --- |
| Propositional evaluation | Generated formulas compared with an independent tuple-tree evaluator |
| Trace correctness | Trace-root values compared with the independent Boolean evaluator |
| Satisfiability and validity | Results compared with complete reference truth tables |
| Returned assignments | Models and countermodels evaluated against their formulas |
| Reachability verdicts | Generated graphs compared with an independent edge-relaxation calculation |
| Shortest paths | Reported path lengths compared with reference shortest distances |
| Counterexample replay | Initial states and named path edges checked against the model |
| Quantifier semantics | Finite-domain checks compared with direct Python quantification |
| Dependent witnesses | Returned witnesses checked against the corresponding outer assignment |
| Budget behavior | Incomplete checks required to return `unknown` or raise the documented limit error |

The standard evaluation uses:

- 1,000 generated propositional formula samples.
- Eight Boolean assignments per generated formula.
- 2,000 propositional search-status checks.
- 200 generated graphs.
- 400 graph invariant/deadlock status checks.
- 50 quantified-property checks.
- Seven model-checking boundary checks.

Generated formulas can repeat. The number of unique formulas is reported
separately in `correctness.json`.

Any differential mismatch causes the script to stop with an error.

### 6.2 Scaling Workloads

Each model family includes faulty and corrected configurations.

| Family | Parameter values | Checked behavior |
| --- | --- | --- |
| Authorization | 1, 2, 4, 6, 8 users | Every granted operation is authorized |
| Lock ring | 2, 3, 4, 5, 6, 7 processes | Absence of nonterminal sinks |
| Bounded buffer | Capacities 1, 2, 4, 8, 16, 32 | Capacity bounds and item-count conservation |
| Propositional validity | 4, 8, 12, 16 variables | Validity of conjunctions of excluded-middle formulas |

Authorization invariants contain a finite-domain quantifier over users.
Counterexamples therefore connect an execution path with the user binding
responsible for the violation.

Buffer models use finite workloads of `capacity + 2` items. They do not model
unbounded production.

The propositional workloads deliberately expose exhaustive enumeration growth.
They are not representative of all propositional reasoning problems.

### 6.3 Evaluation Outputs

| Output | Contents |
| --- | --- |
| `correctness.json` | Sample counts, oracle comparisons, and mismatch counts |
| `benchmarks.csv` | Verdicts, exploration counters, path lengths, timing, and traced allocation peaks |
| `counterexamples.json` | Model counterexample paths and available formula traces |
| `environment.json` | Python/platform information, measurement definitions, and source hashes |
| `unit_tests.txt` | Complete output of the discovered test suite |
| `summary.md` | Readable results and interpretation limits |

The JSON counterexample file records evidence from the run. It is not a
standalone certified proof format.

### 6.4 Timing and Memory Definitions

For each benchmark:

1. The query or exploration is executed repeatedly.
2. Minimum, median, and maximum elapsed times are recorded.
3. An additional execution measures peak Python allocations using
   `tracemalloc`.

Timing includes checking, exploration, predicate execution, and explanation
construction where applicable. Formula and model construction are excluded.

Memory measurement occurs separately from timed executions. The reported
metric is peak traced Python allocation, not process RSS or total system memory.

The harness does not exclude warm-up runs or isolate each repetition in a
separate process. Repeated timings are descriptive measurements rather than
evidence of statistical significance.

PyFinLog runtime and memory measurements characterize its own scaling. They do not
establish performance superiority over other verification tools.

## 7. Logical API

### 7.1 Expression Construction

```python
from tools import var
from logic_core import valid, entails

p = var("p")
q = var("q")

expression = (p & q) >> p

print(valid(expression).status)       # valid
print(entails([p, p >> q], q).status)  # valid
```

| Operation | Syntax |
| --- | --- |
| Negation | `~p` |
| Conjunction | `p & q` |
| Disjunction | `p \| q` |
| Implication | `p >> q` |
| Biconditional | `p.iff(q)` |

Legacy `p == q` constructs a biconditional. It does not test structural equality.

Parenthesize compound formulas because Python operator precedence applies.
Do not construct symbolic formulas using Python `and`, `or`, or `not`.
Implicit conversion of a symbolic expression to a Python Boolean raises
`TypeError`.

### 7.2 Finite-Domain Checking

```python
from tools import var, def_pred
from logic_core import ForAll, check

x = var("x")
Even = def_pred("Even", lambda n: n % 2 == 0)

result = check(ForAll(x, Even(x), [2, 3, 4]))

print(result.status)                 # violated
print(result.trace.decisive_binding) # {'x': 3}
```

Predicates must return actual Python Boolean values. Other data can appear as
predicate arguments, but numeric values and strings cannot stand in for Boolean
formula results.

Quantifier domains must be lists and are shallow-copied during construction.

- Universal quantification over an empty domain is true.
- Existential quantification over an empty domain is false.
- Nested quantifiers preserve local variable scope.
- Evaluation does not modify the caller's context.

### 7.3 Scoped Traces

```python
from tools import print_trace

print_trace(result.trace)
```

Each trace contains:

- The expression's display representation.
- Its Boolean value.
- The current bindings.
- Retained child evaluations.
- A decisive quantifier binding, when applicable.

A false universal retains its first failing instance. A true existential
retains its first successful instance. A true universal or false existential
retains all visited instances.

Traces are execution evidence. They are not minimal explanations, unsatisfiable
cores, or independently certified proof objects.

### 7.4 Propositional Search

```python
from logic_core import satisfiable, valid, equivalent, entails

satisfiable(p & q)
valid(p | ~p)
equivalent(~(p & q), (~p) | (~q))
entails([p, p >> q], q)
```

Search accepts Boolean constants, propositional variables, and connectives.
Predicates and quantified expressions are rejected by this interface.

Search enumerates symbols in sorted order, assigning `False` before `True`.
Its worst-case assignment count is `2^n` for `n` variables.

The default assignment budget is 65,536. An unfinished search raises
`LimitExceeded`.

## 8. Model-Checking API

```python
from tools import var, def_pred
from logic_core import (
    Transition,
    TransitionSystem,
    check_invariant,
    replay_counterexample,
)

model = TransitionSystem(
    initial_states=(0,),
    successors=lambda current: (
        [Transition("increment", current + 1)]
        if current < 3
        else []
    ),
    name="counter",
)

Bounded = def_pred("Bounded", lambda current: current <= 2)

result = check_invariant(
    model,
    Bounded(var("state")),
)

print(result.status)  # violated
print(result.states)  # [0, 1, 2, 3]
print(result.actions) # ['increment', 'increment', 'increment']

assert replay_counterexample(model, result)
```

Invariant formulas access the current state through a variable named `state`.

### 8.1 Result Semantics

| Status | Meaning |
| --- | --- |
| `holds` | Every reachable state satisfies the invariant; exploration completed |
| `violated` | A reachable invariant violation was found |
| `deadlock` | A reachable nonterminal state has no outgoing transitions |
| `deadlock_free` | Exploration completed without a nonterminal sink |
| `unknown` | A checking budget prevented a conclusive result |

`complete=True` means the reachable state space was exhausted.
A counterexample can establish a violation while `complete=False`.

Results record discovered states, checked states, examined transitions,
path states, action labels, and the reason for termination. Invariant
counterexamples also include the failing state's formula trace.

### 8.2 Shortest Counterexamples

Breadth-first exploration returns shortest counterexample paths in transition
count from any supplied initial state.

This does not imply minimum action cost or a unique counterexample.
Ordering among equally short paths depends on initial-state and successor order.

`replay_counterexample()` validates path reachability. It does not establish
shortestness or independently recheck the final property.

### 8.3 Deadlocks and Termination

```python
from logic_core import check_deadlocks

result = check_deadlocks(
    model,
    allowed_terminal=lambda current: current == 3,
)

print(result.status)  # deadlock_free
```

A deadlock is defined structurally as a reachable state with no successors that
has not been designated as allowed termination.

A self-loop is a successor. Consequently, deadlock freedom does not imply
liveness, fairness, or absence of starvation.

### 8.4 Exploration Budgets

Default limits:

| Budget | Default |
| --- | ---: |
| Discovered states | 10,000 |
| Examined transitions | 100,000 |
| Formula-node visits per invariant check | 100,000 |

Example:

```python
result = check_invariant(
    model,
    Bounded(var("state")),
    max_states=100,
    max_transitions=1_000,
    max_steps=10_000,
)
```

Budget-limited exploration returns `unknown`. It never establishes invariant
validity or deadlock freedom.

## 9. Assumptions and Limitations

Verification results apply to the supplied model and specification.

- States must remain immutable and have stable hashing and ordinary Boolean
  equality. Hashability alone does not guarantee immutability.
- Predicate and successor callbacks must be pure, deterministic, and terminating.
- Successor callbacks must enumerate all enabled transitions.
- Budgets cannot interrupt blocking callbacks.
- Quantified checking uses supplied finite interpretations.
- Explicit-state exploration is subject to state-space growth.
- Propositional reasoning uses exhaustive enumeration.
- Temporal logic, fairness, livelock detection, and symbolic arithmetic are not
  implemented.
- Arbitrary Python program verification and automatic transition extraction
  are not implemented.
- A successful check does not establish that the specification captures every
  intended requirement.

The demonstrations are synthetic. They support reproducibility and bounded
correctness observations, not claims of industrial deployment or improved
human usability.

## 10. Troubleshooting

### Import Errors

Run commands from the artifact root, where `tools.py` and `logic_core/` are
located. Confirm that `logic_core/__init__.py` exists.

### Unsupported Python Version

Union type annotations such as `Trace | None` require Python 3.10 or newer.

### Test Discovery Imports Fail

Confirm that `tests/__init__.py` exists and that the complete artifact has been
extracted.

### Non-Boolean Predicate Error

Return `True` or `False`, rather than strings or numeric truth values.

### Symbolic Truth Conversion Error

Use `evaluate()`, `check()`, or inspect a result's `.status`. Do not use symbolic
formulas or result objects directly in an `if` condition.

### Exploration Returns `unknown`

Inspect `.reason`. Increase the relevant budget if appropriate, or reduce the
model. An `unknown` result is inconclusive.

### Deadlock Reported at Normal Termination

Supply an `allowed_terminal` callback defining legitimate terminal states.

### Evaluation Stops with an Assertion Error

The script stops when a correctness check fails. Inspect the traceback and
`unit_tests.txt`. Do not interpret an incomplete run as a successful evaluation.

### Evaluation Stops Before Producing Result Files

Inspect `unit_tests.txt` first. Correctness checks and benchmarks must succeed
before the complete result bundle is written.

## 11. Reproducibility and Interpretation

The evaluation records source-file SHA-256 hashes and environment information.
Rerun the evaluation after changing the implementation or model definitions.

Included reference timings are specific to the machine on which they were
measured. Verdicts, expected reachable-state counts, and documented
counterexample properties should remain consistent under the stated assumptions.

The artifact supports reproducing PyFinLog's demonstrations, correctness checks,
counterexample evidence, and scaling measurements.
